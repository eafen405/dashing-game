# 性能以结构保证，不以基准测试保证

重构期间**不建立性能基准测试套件，也不做反复的实机性能测量**。性能通过结构性设计保证：固定帧预算（16.67ms @ 60fps）、规则层与表现层分离、粒子与刀光使用对象池、Pixi 侧复用 `Graphics` 实例、静态图层仅在 resize 时重建。开发期只提供一个轻量的 FPS / 帧时挂件作为观察手段，CI 不做性能断言。真实性能问题在实机测试阶段反馈。

**为什么**：这个规模的游戏（约 10 个活动实体、粒子上限 260）性能瓶颈几乎全部来自结构性问题 —— 每帧分配、场景树重建、静态内容重绘、O(n²) 查找 —— 而不是需要反复实测才能发现的微观热点。为这类问题搭建基准测试套件与测量循环，成本远高于收益；每次提交都跑一遍测量，噪声还会制造大量假信号。

**帧预算分配**（16.67ms）：

| 段 | 预算 |
| --- | --- |
| 规则层 `tick` | ≤ 1ms |
| 表现层 effects 更新 | ≤ 2ms |
| Pixi 渲染（含 bloom） | ≤ 10ms |
| React / DOM 更新 | ≤ 1ms |
| 余量 | ≥ 2ms |

**后果**：代码评审要盯住分配与重建，而不是盯住微基准数字。以下是已知的结构性性能问题，重构时必须消除：

- `source.html:1989` —— 怪物绘制循环内调用 `monsters.indexOf`，O(n²)。
- `source.html:1633` —— 每帧、每条轨道各执行一次 `monsters.some` 扫描。
- `source.html:978` 等 7 处 —— 用 `filter` 重建整个 `monsters` 数组代替就地移除。
- `source.html:1276` —— `loop` 内每帧调用 `syncHUD()`，靠脏标记兜底；新实现改为事件驱动的订阅。

**现状**（2026-10）：以上四个结构性热点均已消除 ——

- ① `monsters.indexOf(p)` 的 O(n²) → 渲染器每帧预扫出"链主 = 上轨那只"，O(1) 判定（`battlefield/pixi/twin.ts`）。
- ② 每轨一次的 `monsters.some` 全量扫描 → 一次遍历同时算出两轨的"有长按怪"标志（`battlefield/pixi/PixiRenderer.ts`）。
- ③ 7 处 `filter` 重建 `monsters` 数组 → 收敛为**每 tick 一处**（`game/rules/tick.ts`），且只回收已离场的怪物。
- ④ 每帧 `syncHUD()` → 事件驱动的 `hudStore` 订阅（`app/hud/hudStore.ts`）。

CI 仍不做任何性能断言；帧预算分配见上表，未做实机测量。

（票 18）CI 里最后一条隐含的帧率断言也已拆掉：e2e 的 HUD 统计脚本原先用
`publishes > 600`（30 秒 600 次 ≈ 20fps）判「循环在跑」，实际是一条帧率下限，
判据绑在跑测试那台机器有多快上。现在换成**结构性判据**（循环没冻 / 每帧发布一次），
同类的「出刀次数」判据也改成相对量 —— CI 里已没有任何一条判据取决于机器速度。
