# 端到端测试推迟到收口阶段补上

规格阶段把「引入端到端测试」列为**非目标**（第二阶段再议）。实际执行时这条被反转：重构的**收口阶段**补上了 13 个端到端脚本（`tests/e2e/*.mjs`），并把它们接进 CI（`npm run test:e2e` 与 `npm run test:visual`）。

**为什么**：规格里的验收标准有一大半是**视觉与交互**的 ——「暴击的粒子是碎片形」「FEVER 期间画面仍然可读」「判定框落在棒尖攻击范围内」「长按怪头部进圈后按住 2 秒能贯穿」。这些标准在写规格时是**给人眼**的：靠人看截图判断，没有脚本就谈不上「达标」与「不达标」。收口阶段（票 05 / 18 / 19 / 20）把它们改写成**可判定的断言**（toast 文案、分数增量、画面几何、像素差），验收标准才真正可执行。

这也正是 ADR-0004 要求的落点：CI 的判据要是**结构性的**（不取决于跑测试那台机器有多快），而端到端脚本就是把「看起来对」翻译成「结构上对」的地方 —— 例如 HUD 统计脚本原先有一条隐含的帧率下限（`publishes > 600`），票 18 把它拆成了结构性判据。

**后果**：

- CI 多两个 job：`e2e` 与 `visual`，视觉验收单独一个 job（与 `verify` 并行、各 30 分钟预算），失败即红；验收拼图作为 artifact `visual-acceptance-shots` 上传 —— `dist/` 被 gitignore，不留档就对任何后来人都不可见。
- 端到端脚本依赖 `dist/` 产物：改了 `src/` 必须先 `npm run build`，否则跑的是旧产物。
- 视觉脚本的耗时有**分布**（`fx-moments` 打的是真实对局，900 轮搜索可能跑满），CI 上要留超时余量。
- 「第二阶段再议」不再成立 —— 规格的「非目标」一节已随之改写。

**现状**（2026-10）：13 个端到端脚本已入库（`tests/e2e/`），`npm run test:e2e`（6 个脚本）与 `npm run test:visual`（6 个脚本）在本机全绿，CI 里是两个独立 job。规格「非目标」一节已改写为「推迟 → 收口阶段补上」，并指向本决策。
