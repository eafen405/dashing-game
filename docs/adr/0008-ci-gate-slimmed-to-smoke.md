# 门禁收口成一条冒烟：视觉脚本本地跑，黄金轨迹比对手动触发

**状态**：已采纳（2026-10-23）

## 背景

重构（0.2.0）已经结束并合进 `main`。但围着它搭的验收体系是按**「还要再重构一次」**
的假设建的，重量没有跟着项目阶段收：

| 东西 | 行数 / 体量 | 为什么已经不划算 |
| --- | --- | --- |
| 逻辑层（`src/game/`） | 3196 行 | 这才是产品 |
| 整个产物（`src/`，不含测试） | 12718 行 | 其中 `src/battlefield/`（PixiJS 渲染）就占 5329 行 |
| 单元测试（`src/**/__tests__/`） | 5899 行 | **比例合理**，而且极便宜 —— 保留 |
| e2e 脚本（`tests/e2e/`） | 3733 行（12 个脚本） | 完整跑一遍约 20 分钟 |
| 工具脚本（`scripts/`） | 2272 行 | 其中 `trace-gate` 值得留 |
| CI | 2 个 job，各自 30 分钟预算 | 实际耗时贴着 30 分钟超时线 |

**测试代码量是产物的 0.94 : 1**，对一个「做着玩」的项目，这个比例意味着
**验收体系本身成了需要维护的产品**。

## 决策

**push 门禁收成一条 30 秒的冒烟，其余全部移出 CI。**

| | 原来 | 现在 |
| --- | --- | --- |
| push 门禁 | `verify` job：typecheck → lint → test → build → verify → **完整 e2e** → **trace**<br>`visual` job：6 个特效脚本 | `verify` job：typecheck → lint → test → build → verify → **冒烟 e2e**（20 秒） |
| `visual` job | 有，与 `verify` 并行 | **删掉** |
| 黄金轨迹比对 | push 门禁 | **`workflow_dispatch` 手动触发**，job 与脚本都保留 |
| 完整 e2e（12 脚本） | 门禁 | 本地 `npm run test:e2e` |
| 特效视觉脚本（6 个） | 门禁 | 本地 `npm run test:visual` |

### 保留了什么

- **单元测试全部保留**，而且它们是最便宜的一层（417 个用例，约 1 秒）。
  「测试太多」从来不是问题 —— **慢的、脆的、只在特定时候有意义的**才是。
- **lint / typecheck 保留**（各约 5 秒）。
- **12 个 e2e 脚本与 6 个视觉脚本一个都没删**，只是不再每次 push 都跑。
- **golden trace 与它的回放器全部保留**，`npm run trace` 本地随时能跑。

### 冒烟守什么

`tests/e2e/smoke.mjs`（新增，20 秒）走一条路径：

```
开机 → 难度屏 → 玩法说明屏 → 开局 → 出刀命中 → 暂停 / 恢复
     → 结算 → 「选择难度」→ 难度屏 → 回主页面
```

断言全部落在**可观察的 DOM 状态**上（元素文本 / 类名 / HUD 数值 / 路由）。

**它守的是「这个产物还能玩」**，不是「每个细节都对」。
门禁存在的意义是**挡住「推上去就坏了」**，不是**挡住「改错了但没被发现」** ——
后者是本地跑完整套的职责。

## 为什么这么切

**黄金轨迹比对降级为手动** —— 它回答的是「重构前后行为是否逐帧一致」。
重构已经结束，所以从今往后它挡的是「我自己改规则层时有没有偷偷改变行为」。
这件事**值得盯**（规则层是纯函数、逐帧可复现，天然适合这种检查），
但不值得让每次 push 都多付一遍时间。
**代价要说清**：以后规则层改了、门禁没跑，这个分叉就永远发现不了了。
真要守，就手动触发一次 —— 这条路还在。

**视觉脚本移出 CI** —— 这里要纠正一个常见误解：这些脚本的判据**不是绝对像素阈值**，
而是**相对 / 结构性**的：

- `bloom-ab.mjs` 比的是**同一次运行里** bloom 开与关两张图的平均亮度；
- `fx-fever-readability.mjs` 比的是同一次运行里色散前后的通道分离度；
- `filter-center-probe.mjs` 判的是两次触发之间**差值图非空**；
- `hold-monster-keyboard.mjs` 与 `fx-moments.mjs` 干脆是**行为断言**（toast 文案、
  分数增量、瞬间个数），一个像素都不看。

也就是说**换台机器、换个显卡驱动不会让它们飘** —— 判据的两边都来自同一次会话。
把它们移出 CI 的理由**不是脆，是慢**：SwiftShader 软件光栅下整套装机要 3.5–8 分钟，
而且只在「改了视觉」时才有意义，不该每推一次都付。

**CHANGELOG 收口** —— D1–D17 那份清单在 CHANGELOG 和 `.scratch/refactor/spec.md`
里**各存了一份**，而 spec.md 那份带**判定 / 说明 / 验证方式**三列，更全。
CHANGELOG 里这份是复制品，读者只有作者本人，所以撤掉，**指向 spec.md**。
差异本身**一条没少、没重编号**。

**从 0.3.0 起 CHANGELOG 改用「按版本记」** —— 每次玩家可见的改动写进新版本段
（0.3.0 段就是这么写的）。这个纪律保留，因为它便宜，而且**它才是 CHANGELOG 的用途**；
「复刻期的一次性审计」不是。

## 后果

- **push 门禁约 2 分钟**，`timeout-minutes` 从 30 降到 10 —— 「作业超时」这个概念
  从项目里消失了。
- `feat/**` 分支的 push **仍然跑门禁**（2 分钟，很便宜）。
  砍掉它会让「没开 PR 就推」的场景完全没有反馈，得不偿失。
  （真正贵的是「完整验收」，不是「push 就跑」这件事本身。）
- **冒烟用 4★ 开局**：结算要等血量掉光（250 点，每漏一只 −20）。
  1★ 要 46 秒，4★ 只要 13 秒 —— 冒烟要的是快，不是温和。
  注意无头 Chromium 的帧步长被钳在 50ms（`dt = min(dt, 0.05)`），
  SwiftShader 下模拟推进只有实时的约 60%，CI 上这个数字会变成约 22 秒。
- **规则层以后不受任何自动门禁保护**。改 `src/game/**` 的人要自己记得跑
  `npm run trace`。这是本决策最实在的代价，写在这里以免日后被忘掉。
- 完整 e2e 与视觉脚本现在**只在本地跑** —— 意味着它们**会慢慢腐化**。
  这是接受的代价：它们的价值本来就在「改视觉时手动看一眼」，
  而不是「每次 push 跑一遍」。

## 顺带修掉的

冒烟的编写过程里发现**帧步长钳制**（`dt = min(dt, 0.05)`）会让模拟在低帧率下
比实时慢（SwiftShader 下约 60%）。这不是 bug —— 照抄旧版 `source.html:1282` ——
但它决定了冒烟要用 4★ 才能压进 30 秒。记在这里，免得下次有人以为「等结算要 46 秒」
是设计出来的。
